# Web 基盤 要件定義書（米川 明希 担当）

> **担当**: 米川 明希
> **対象**: 注文画面・ダッシュボード・分岐器の通常動作・タスクログ・DB・テスト
> **更新日**: 2026-10-25

---

## 1. 目的

ProofPick の Web 系基盤を定義する。ここでは**判断ロジック（何を選ぶか）は作らない**。
「注文を受け付けて、実行基盤に渡し、結果を店舗側に見せる」ことだけを担う。

---

## 2. 対象範囲

| 項目 | 内容 |
|---|---|
| Web 注文画面 | 顧客が商品を注文する UI |
| ピッキング管理ダッシュボード | 店舗がタスク・ロボット状態を見る UI |
| 分岐器の「通常動作」登録 | 定型注文パターンの登録 |
| タスク実行ログ | 注文・タスク・完了証跡の記録 |
| 商品マスタ DB 連携 | 商品・価格・アレルゲンの参照 |
| テストハーネス | 注文フローの自動テスト |

---

## 3. システム概要

```
顧客 ── Web 注文画面 ──> 実行基盤 ──> ロボット
                              │
店舗 <── ダッシュボード <──────┘
```

---

## 4. 機能要件

### 4.1 Web 注文画面

| 機能 | 内容 |
|---|---|
| 商品検索 | 商品名・カテゴリで検索 |
| カート | 複数商品の追加・削除 |
| 条件指定 | アレルギー（小麦不使用）・優先条件 |
| 注文確定 | 実行基盤へ注文データ送信 |
| PII 表示 | 個人情報はマスク済みの状態で送信 |

### 4.2 ピッキング管理ダッシュボード

| 機能 | 内容 |
|---|---|
| 注文一覧 | 受注中の注文を表示 |
| タスク状態 | 各タスクの進捗（待機/実行中/完了/失敗） |
| ロボット状態 | 位置・電池・エラー表示 |
| 完了証跡の表示 | 「なぜその商品を選んだか」の根拠表示 |

### 4.3 分岐器の「通常動作」登録

- 「牛乳1本」「卵1パック」等の**定型注文パターン**を正規表現で登録
- 定型パターンは LLM を介さず**直接 Lookup へ**振り分け
- 判断の核心（分岐器の分類ロジック）は**村上が担当**。ここでは「登録データの管理」のみ

### 4.4 タスク実行ログ・商品マスタ DB

- 注文・タスク・完了証跡（座標・JAN・トルク）を記録
- 商品マスタ（商品名・価格・アレルゲン）の参照・更新
- ログは改ざん検知のため、ハッシュを併記（村上の署名機能と連携）

### 4.5 テストハーネス

- 注文フローの自動テスト（受け付け→トリアージ→Lookup→完了）
- 分岐器の通常動作パターンの回帰テスト

---

## 5. 非機能要件

| 分類 | 要件 |
|---|---|
| 性能 | 注文画面の応答 200ms 以内 |
| 可用性 | 実行基盤が落ちても注文はキューに保持 |
| セキュリティ | 顧客 PII は Web 側では保持しない（実行基盤側でマスク済み） |
| 拡張性 | 商品マスタの追加が容易な設計 |

## 6. インターフェース（実行基盤との連携）

```json
// 注文確定（Web → 実行基盤）
{
  "order": "カレー用の野菜と小麦不使用のルー",
  "requirements": { "allergen": "小麦 不使用" },
  "customer_id_masked": "****"
}
```

```json
// 完了証跡（実行基盤 → ダッシュボード）
{
  "decision": "候補B（米粉カレールー）",
  "evidence": { "bbox": "[220,40,80,60]", "log_line": "2057" },
  "status": "completed"
}
```

---

## 7. 受け入れ基準

- [ ] 注文画面で商品を検索・カート・注文確定できる
- [ ] ダッシュボードで注文・タスク・ロボット状態が見える
- [ ] 定型注文パターンが登録でき、LLM を介さず Lookup へ振り分けられる
- [ ] 完了証跡（座標・JAN）がダッシュボードに表示される
- [ ] 注文フローの自動テストが通る
